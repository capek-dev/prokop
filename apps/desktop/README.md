# Prokop native desktop experiment

This is an experimental native GPUI window for [Slice A](../../docs/v2-native-desktop-and-harness-host.md), not a WebView or a replacement for the web client. It lists sessions via HTTP in a searchable GPUI Kit `List` that renders visible rows, offers host-scoped project and session creation, loads the latest 50 transcript messages and shows 10 at a time, and connects to the selected session over the host WebSocket. The selected session can display live text updates and, when this desktop owns session control, queue a chat message or request interruption. Approvals and questions still require the web client. Manual retesting confirmed that session navigation and transcript scrolling no longer lag after the virtualized sidebar and optimized debug profile changes. Transcript paging remains a temporary cap, not a virtualized conversation view.

## Check without starting a host

```sh
cargo fmt --check --manifest-path apps/desktop/Cargo.toml
cargo check --offline --locked --manifest-path apps/desktop/Cargo.toml
cargo test --offline --locked --manifest-path apps/desktop/Cargo.toml
```

Focused Rust tests cover HTTP envelopes, attach response validation, auth failure copy, host-scoped snapshot retention, filtering across 240 sessions, transcript paging, wire event shapes, resume gating, retry backoff, queued-command discard, and cancellation. Manual testing against a running host confirmed attach, disconnect, and reconnect. To manually retest the new attach-or-start path, use the paired release build described below, not `cargo run` (which does not place a bundled host beside the debug executable).

## Preview configuration

When approved for a manual run, the window probes `http://127.0.0.1:8742`. `PROKOP_DESKTOP_LOCAL_URL` overrides this address but automatic launch only accepts loopback HTTP. An existing host must expose an `installationId` matching the `installation-id` file in its resolved data root (`PROKOPAI_DATA_DIR`, legacy `JEAN2_DATA_DIR`, or the host default). Older hosts must be upgraded; a mismatched host, occupied port, or auth error never triggers another launch. If the port refuses connections, the root already has an initialized config and default database, and no custom database/TLS override is detected, the desktop starts only the `prokop` executable beside its own binary via the host's detached `start` command. It does not stop the daemon on window close. Initialization and existing custom database settings must be handled with the web/CLI host until native setup exists. The isolated-root attach-or-start path passed a user-operated host test; these guards are not a cryptographic host identity.

For a local development pair on macOS arm64, run `bun apps/desktop/build-local.ts` from the repository root (builds the client, compiled host, and Rust release binary and places `prokop` beside `prokop-desktop` in `apps/desktop/target/release/`). Do not run the desktop binary or start a host without explicit permission. The command ad-hoc signs and verifies the compiled host, then checks its `version` command before copying it; this fixes a macOS linker signature that otherwise causes the preview host to exit before launch. It is a build recipe, not a signed `.app` or an installer, and has not been verified on a clean machine. For an isolated initialized data root, set `PROKOPAI_DATA_DIR` and a dedicated loopback `PROKOP_DESKTOP_LOCAL_URL` together. If TLS is enabled in your shell, set `PROKOPAI_TLS_ENABLED=false` and `JEAN2_TLS_ENABLED=false` for this local test only. Check the selected database path first and never point a preview at the personal production root. If the host requires auth, export `PROKOPAI_AUTH_TOKEN` before opening the desktop. The WebSocket passes it in `/ws?token=`, so avoid logging that URL. A second HTTPS origin can be supplied through `PROKOP_DESKTOP_REMOTE_URL`, but authenticated remote setup and secure credential storage are not implemented. Do not put tokens in configured origin URLs.

The current host labels are temporary connection IDs (`This machine` and `Remote`), not durable host identities. Do not use these as persistence keys. The selected session's worker reconnects after transient WebSocket failures with a 1 to 8 second backoff; each connection registers again and reloads the host's authoritative latest 50 messages before accepting deltas or enabling Send/Interrupt. The visible transcript stays on screen while disconnected. Queued actions are discarded during retry, and a send that lost its connection may have reached the host, so check the transcript before resending. Authentication rejection and a missing session stop retries. Switching sessions cancels the previous worker. Sending, streaming, interruption, and reconnect were manually verified against an existing host. This is not host-wide event recovery: workspace/session lists still need an explicit Refresh hosts, and older transcript pages are not restored. Local attach-or-start passed a user-operated isolated-root test. Project and session creation still need user-operated E2E verification; creation waits for a host response, then refreshes the authoritative list, and does not retry POST requests automatically. Remote credentials, a persistent multi-host index, independent two-host verification, and the rest of web-client workflow parity remain open.
