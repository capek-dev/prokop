### Added

- Server-log diagnostics for Claude CLI and Codex CLI turns (`harnesses/shared/diagnostics.ts`). A failed prompt used to reach only the WebSocket connection that sent it, which is often gone for queued prompts, and Codex intentionally hides upstream detail from clients, so a prompt could fail with nothing on the server to debug. The shared CLI queue now logs every error a turn sends (`[claude-cli] prompt failed` / `queued prompt failed`, with session, code, and message), exceptions that escape a turn (`turn threw`), and a queue that stops with a message still pending (`queue stopped`). Each turn logs `turn start` (model, effort, resume, goal, queued) and `turn completed` with its duration; failures log `turn failed` with the phase, error type, bounded message, top stack frames, and the tail of the CLI's stderr (Claude through the SDK `stderr` option; the Codex app-server's stderr is now piped instead of ignored). Codex also logs the RPC code, whether the turn may have run, turns Codex itself reports as failed with its error message, the upstream text of rejected requests (kept on `CodexRequestError.detail`, never sent to clients), and app-server processes that exit without being closed. Both harnesses log which condition blocked a turn on a stale native binding (pending earlier turn, workspace change, or CLI version change, with both versions). Prompt and reply content is never logged.
- Event-loop stall diagnostics. With `PROKOPAI_PERF_DIAGNOSTICS=true`, a 100ms interval measures how late it fires and logs `[perf] event-loop stall <ms>` whenever the server was blocked for longer than `PROKOPAI_PERF_STALL_MS` (default 50). Each line lists in-flight HTTP requests and what ran during the stall: HTTP routes, inbound WebSocket message types, and outgoing event types (repeats counted), with the synchronous part of any handler or send that took 10ms or more. A stall with no breadcrumbs points at a timer or stream callback. Everything is a no-op when diagnostics are off (`utils/stall-monitor.ts`).
- Settings gains a Usage tab that shows plan limits for the Claude CLI and Codex CLI harnesses. A new `GET /api/harnesses/:id/usage` (SDK `sessions.harnessUsage`) reads each CLI's own login on demand: Claude through the SDK `get_usage` control request (`usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET`, so the shape may change) on the same no-prompt probe the model catalog uses, and Codex through `account/rateLimits/read` on a short-lived app-server. Both map onto one `HarnessUsageLimits` shape (5-hour, weekly, monthly, and per-model weekly windows with used percent and reset time); Codex windows classify by `windowDurationMins` and only the main `codex` bucket counts. API-key logins report `unsupported` and a failed read reports `probeFailed`, each with a message instead of bars. Reads share a 30-second server cache so reopening the panel does not spawn a CLI each time, and the panel only fetches for installed, enabled harnesses, with a refresh button per card. Prokop is left out for now. Live updates during turns (`rate_limit_event`, `account/rateLimits/updated`) are not wired yet.

### Fixed

- Git status is now pushed by the server instead of refetched by every client after every tool call. Each file-mutating tool completion (including read-only `shell` calls) broadcast `files.changed`, and every connected client then refetched Git status, diffs, tree, worktree refs, and four unscoped query families (repository, branches, history, rebase) for every open workspace, with each `git/status` request spawning 6 `git` processes (one server log showed about 15,000 status calls). A server-side `GitStatusFeed` (`application/files/git-status-feed.ts`) now computes status once per workspace root for all subscribers: tool completions open a 250ms collect window, computes run at most once per 2s while changes keep arriving with a guaranteed final run, and Git actions from the app or a client focus refresh run immediately. It pushes a new `git.status` message only when the status fingerprint changed; HTTP `git/status` reads share the same serialized runner. The SDK adds `git.status.subscribe`, `git.status.unsubscribe`, and `git.status.refresh` (`client.git`); the client ref-counts subscriptions per root, re-sends them after reconnecting, writes pushed snapshots straight into the status query (older revisions are ignored), and refreshes repository, branches, history, rebase, and worktree refs only when the pushed HEAD commit or branch changes, so commits made by agents still reach the Branches panel. `files.changed` now only invalidates file listings, search, previews, and diffs, and `git.changed` invalidates branch views for its own workspace only. Status responses gain `head` (`{ oid, branch }`) and `revision`; `git --version` is cached per process and the repository root per path, so a refresh spawns 5 processes instead of 6. Commits typed in terminals and edits from external editors are picked up on window focus or the next tool completion, not live.
- The file tree is now pushed by the server instead of refetched by every client after every tool call. Each `files.changed` made every connected client refetch the full recursive path list of every mounted tree root, including hidden explorer views, and the client rebuilt the whole Pierre model (`resetPaths`) whenever a path was added or removed. On a 20k-entry workspace that was a 105ms walk and a 1.8MB response per tool call per client, plus a 24ms rebuild, even though most tool calls (edits, read-only `shell`) leave the path set unchanged. The scheduling core of the Git status feed moved into a shared root feed (`application/files/root-feed.ts`), and a `FileTreeFeed` (`application/files/file-tree-feed.ts`) on top of it walks each watched root at most once per 2s while changes arrive (with a guaranteed final walk), pushes nothing when the paths are unchanged, and otherwise sends only the added and removed paths on top of the subscriber's revision (the whole tree for new subscribers, or when the change is larger than the tree). App create, rename, and delete, and app Git actions refresh the tree (and Git status) immediately; HTTP `files/tree` reads share the same runner and serve the cached tree for watched roots, while `showHidden=false` and invalid roots keep the direct walk and its errors. The SDK adds `files.tree.subscribe`, `files.tree.unsubscribe`, and `files.tree.refresh` (`client.files`), the `files.tree` message, and `FileTreeResponse.revision`. The client shares the ref-counted subscription helper with Git status (`lib/rootFeedSubscriptions.ts`: reconnect resubscribe, focus refresh), applies a delta only on top of the exact cached revision (a missed revision refetches), and patches the Pierre model with a normalized `batch` (0.24ms for a small change) that keeps expansion, selection, and scroll, falling back to `resetPaths` for the first load, changes over 2,000 paths, or a failed patch. `files.changed`, `git.changed`, the Branches refresh, and file actions no longer invalidate the tree; the manual refresh button asks the feed to rewalk.
- The Files panel refresh button and explorer and editor file operations update the Changes tab again. Since the Git status feed, HTTP reads of a watched root returned the feed's cached snapshot, so the refresh button (Explorer and Changes) re-read the same state, and deleting, creating, or renaming a file in the explorer or saving in the editor left Changes stale until the next agent tool call or window focus. App create, rename, delete, and editor save now refresh the root's Git status and tree at once (pushed to every subscriber), and `GET git/status` and `GET files/tree` accept `refresh=true` (SDK `refresh: true`), which recomputes instead of serving the cache. The refresh button uses it for Git status and the tree and keeps spinning until both return, so changes made in a terminal or another editor show up on click.
- The server no longer stalls while Claude CLI and Codex CLI sessions stream. Two kinds of main-thread work blocked HTTP, WebSocket, and terminal traffic. (1) `claude --version` and `codex --version` ran through `Bun.spawnSync` on every harness status read, model catalog read, session create, and turn (6 blocking probes per `GET /api/harnesses`, about 35 to 50ms each). The probes are now memoized per executable identity (`harnesses/shared/cli-version-cache.ts`: resolved path, inode, size, and mtime), so they cost about 0.03ms and re-probe only when the binary changes, which keeps the exact-version binding checks correct after a CLI upgrade. (2) Both harnesses and their subagent timelines called `updatePart` on every streamed text delta: a read-before-write, a full-text rewrite, and a search reindex of the whole message, growing with message length. A shared `StreamingTextWriter` (`harnesses/shared/streaming-text.ts`) now mirrors Čapek's stream handlers: clients still get every `part.append`, SQLite gets a plain snapshot at most every 300ms, and the final text is written once with search indexing when the segment ends (Claude `text-final`, tool start, turn end, failure, or Stop; Codex `item/completed`, continuation, turn end, or failure). Settled segments are re-sent as `part.updated`, so a client that loaded the transcript between snapshots converges.
- Claude CLI Read rows no longer render the file contents as a code block labeled "Overwrote". The Claude visualizer mapped `read-file` to a `code` visualization with `created: false`, which `CodeBlock` labels as an overwrite. Reads now render as a path chip (`Read: <path>`), the same as the Prokop read-file tool. Rows already persisted in older sessions keep their stored visualization.
- Codex CLI shell rows no longer render an empty output body of literal quotes. Codex reports command output as a JSON-encoded string, so a command without output arrived as the bare encoded empty (`""`, sometimes `[]`) — truthy, so the transcript rendered a body block containing just `""`. The adapter's command rows now collapse bare encoded empties to empty stdout (`commandStdout` in `harnesses/codex-cli/tool-items.ts`), and the client `TerminalOutput` suppresses whitespace-only stdout/stderr in both its header and headerless variants, so a shell row with nothing to show renders the command header and exit code only. Rows already persisted in older sessions keep their stored stdout.
- Claude CLI and Codex CLI sessions now send web-push notifications for finished replies and waiting permission asks. Only the Prokop runtime called the notification application (through Capek host events), so with the PWA closed or in the background, native-harness chats never pushed "completed", "failed", or "permission required"; in-app sounds were unaffected because they key off the shared `message.updated` and `ask.request` events. A `HarnessNotificationPort` (`application/ports/harness-notifications.ts`, installed in bootstrap over the existing notification application) is now called from both harnesses through `harnesses/shared/notifications.ts`: when a top-level reply reaches a terminal status (Claude turn end, Codex `turn/completed`, failed setup, and recovered turns) and right after an ask is sent to the controller. The existing policy still decides delivery (completed and error notify, interrupted and child sessions do not, scheduled jobs follow their opt-in, a client watching the session acknowledges and suppresses the push). Codex goal runs push only when the run ends, not on each continuation turn, and learning review sessions never push.
- Claude turns no longer fail with "Claude CLI event outside turn (before init: system/commands_changed)". The CLI watches its own commands and config, so opening Claude Code in another terminal can make it emit `system/commands_changed` before this turn's `init`, and the turn reader failed closed on any pre-init message. Content-free notices (`commands_changed`, `background_tasks_changed`, `session_state_changed`, `status`, `notification`, `informational`, `plugin_install`, `files_persisted`) are now skipped before init; turn content (assistant, user, stream, result, task events) before init still fails closed. Manual compaction skips `commands_changed` the same way.
- Editing a Claude message right after stopping its reply no longer fails with "Claude conversation cannot be edited at this point". Edit and Undo matched the entire native history against the local transcript, and a stopped turn never matches (its local reply is `interrupted` and Claude may have written only a partial native turn). When the rollback discards a stopped or failed turn, only the kept turns are now verified (`matchClaudeHistoryPrefix`), and rolling back to the first message no longer reads native history at all. Rollbacks over fully completed history still require the whole history to match.

- Stopping a Claude turn no longer locks the session. Stop left the native session binding `pending`, so the next message failed with "Claude turn requires reconciliation". After stream and tool cleanup, an explicitly stopped ordinary turn now releases only its own binding and the next message resumes the same native conversation. Goal turns, history-edit resubmits, and earlier failures stay locked for reconciliation, and the stopped prompt is never replayed.
- Allowed paths no longer trigger outside-workspace asks, and Codex sandbox escalations follow the session mode. Native harness permission checks only ever received the session root, so Codex or Claude reading a skill from the agent's own directory, or touching a workspace additional path, asked as an escape even on standard. A shared `sessionPermissionRoots` (`harnesses/shared/permission-roots.ts`) now defines the allowed roots for all harnesses: the selected root plus workspace additional paths (dropped in managed worktree sessions, like the Prokop tool host) are read/write roots; the session agent's directory (skills, home, memory files) and the uploads dir are read-only roots. The shell analyzer and `classifyFileOperation` accept read-only roots, which satisfy reads, searches, `<` redirects, and operands of read-only commands (`cat`, `head`, `ls`, `grep`, `rg`, `diff`, `find` without acting predicates, ...), while writes, `>` redirects, patches, and deletes there still escape. The Prokop tool host adds the agent directory to its allowed paths, shell/terminal pass additional workspace roots through, and grep/glob honor allowed paths like read-file. Separately, Codex native command escalation (`requestApproval`, raised when Codex's sandbox blocks a command such as `git add` writing `.git`) classified the command but always asked; it now auto-approves through `shouldAutoApproveAsk` like the hook path, so clean commands run at standard while escape, sensitive, destructive, and catastrophic findings still ask per mode. File-change escalations carry no paths and still ask.
- All three harnesses now analyze file operations through one classifier and emit the same permission-ask shape. Shell commands already shared `classifyShellCommand`; file operations did not: Claude's adapter hand-rolled concerns with shared helpers, Codex's apply_patch hand-rolled different concerns over a hard-coded `risk: 'high'`, and the Prokop file tools (edit, write-file, read-file, grep, glob, file-to-markdown) pinned `risk: 'medium'` with no concern fields at all. A new `classifyFileOperation` (`domains/permissions/file-ops.ts`) is now the single policy point — escape (outside all allowed roots, symlink-resolved), sensitive (path or search pattern), destructive (deletes), risk derived via `concernRisk`, scopes via `grantScopesForFinding` — and every path consumes it: Claude Read/Edit/Write/Glob/Grep, Codex apply_patch, and the Prokop tools via an enrichment helper that keeps each tool's question and `permissionKey` grant key intact. Intended behavior changes: sensitive-file asks from Prokop tools now derive `high` risk (medium ceilings such as capek auto-approve at 'medium' no longer auto-approve sensitive reads/writes/edits/searches — matching Claude and Codex, where sensitive asks in every mode), glob gains a sensitive-directory ask (parity with grep and Claude Glob), and Codex apply_patch escape-only patches display medium instead of the old blanket high (the decision flow was already keyed on concerns). Decision authority is unchanged (`shouldAutoApproveAsk`/`requiresHumanReview`), and the client dock cards now show concern chips and severity colors for Prokop file asks too.
- The Files panel now reflects filesystem changes from every writer, not just the session in view. Tool completions were only delivered to session participants (`broadcastToSession`), so files written by subagent child timelines, background agents, learning-harness runs, or any session in another pane never refreshed the tree, search, git status, preview, or diffs — and a burst of completions fired a burst of un-debounced invalidations. The message store (the persistence choke point every harness funnels through: the prokop runtime via capek's `updatePart({ state })` tool transitions, Claude CLI and Codex CLI via `transitionToolTo*`) now classifies terminal tool parts by canonical name and notifies a workspace listener wired to a workspace-scoped `files.changed` broadcast; the client debounces it per workspace (300ms) into a single invalidation of browse/tree/search/git-status/git-diff/preview. Classification (`isFileMutatingToolName`, shared SDK const) covers the builtin writers (edit, write-file, shell, terminal, cp, mv, mkdir, touch, ln) plus Claude's canonicalized forms (`Bash`→shell, `Edit`/`MultiEdit`/`NotebookEdit`→edit, `Write`→write-file) and Codex's (`commandExecution`→shell, `fileChange`→edit); error and interrupted completions count as writes (partial writes are real). The participant-side `part.updated` fallback now resolves the session's workspace and routes through the same debounce (and covers the wider name set), Claude/Codex revert dispatch and the native `session.reverted` event invalidate as well, and MCP/custom tools remain unclassified by design (names alone cannot classify them). Previews and diffs also catch up on reopen: the preview and diff queries pinned `refetchOnMount: false` with an infinite cache lifetime, so a file previewed before an agent's change kept showing the stale cached diff after reopening — only the manual refresh button updated it; they now refetch on mount when invalidated (first opens stay instant, because the infinite stale time means only an invalidated query refetches). And since agents run git through the shell without emitting `git.changed` (which only UI/workbench mutations emit), `handleFilesChanged` reuses the `git.changed` invalidation set, so agent-made commits refresh git history, branches, repository, rebase state, and worktree refs too — not just status.
- Learning history links open their sessions instead of an empty view, and agent homes lose the Learning settings tab. The history dialog's "Open learning session" and source-conversation rows were plain router links: for sessions outside the active workspace (agent-home review sessions, cross-workspace sources) they only changed the URL — nothing fetched the session, switched the workspace, or opened the board pane, so the view sat on an eternal skeleton. They now call `resumeSession` (via the session manager, whose provider in `ServerShell` now also wraps `ServerDialogs`) and close the settings dialogs; `resumeSession`'s fetch-unknown-session path also switches the active workspace once the session's workspace is known. Run labels no longer read "Unavailable learner": agent-home runs record the agent id as the reviewer id, so `LearningHistory` falls back to resolving that id as a preconfig name (stored home settings can carry an inert legacy reviewer). Copy consistency: the history link and dialog title read "History" (not "Learning history") in both the workspace Learning panel and the agent editor, and `WorkspaceSettingsDialog` drops the Learning section entirely for agent homes (stale selection falls back to Agent Tools) since agent learning is configured on the agent; `LearningPanel` deletes its agent-home branch and `personal` conditionals (source selection lives on the agent; the "Use as personal learning source" toggle stays for regular workspaces).

- Agent learning now triggers for Codex/Claude CLI sessions and its harness reviews actually run. Two failures compounded: (1) agent-scope learning evidence requires the message row's `agent` to equal the agent id, but the codex/claude executions never stamped it (only the prokop runtime did), so harness sessions could never become evidence and runs stopped triggering after the first backfill; both harnesses now stamp `agent: session.agentId` on assistant messages (top-level turns, continuation turns, and subagent child timelines — `agent` is an assistant-message field in the contract, user messages carry none). (2) Agent home workspaces are created virtual, and both CLI runtimes rejected virtual workspaces before writing anything; the pre-turn throw was converted to a wire error that the headless no-op wire swallows, so the one review that did dispatch "completed" in 7ms with a zero-message review session. A shared `cliWorkspaceAvailable` type guard (`harnesses/shared/cli-workspace.ts`) now exempts agent homes (virtual rows backed by a real home directory) across claude send/rollback/fork/compact and codex's workspace root, and `bootstrap/learning.ts` guards the dispatch: a headless run that resolves success without writing an assistant message to its review session fails the run with "Harness review turn did not run" instead of recording a green no-op. Existing harness sessions without stamped messages stay ineligible (no backfill migration); new turns work from the first message.

- Claude Code 2.1.x model pickers show real model names again. The new CLI catalog flipped its display format: `displayName` now carries the full model name ("Opus 5.5") while `description` became a pure capability blurb ("For complex work and everyday tasks"), and the same model appears twice — a `default` alias row labeled "Default (recommended)" plus the concrete row. The catalog parser (`harnesses/claude-cli/models.ts`) built names from `description.split(' · ')[0]` first (a hack for the old format, where display names were bare ("Opus") and the versioned name led the description "Opus 4.6 · ..."), so every picker row showed its blurb; and the dedup kept the first row per model id, so Opus 5.5 also showed as "Default". The parser now trusts `displayName` and only uses the description segment when it extends the display name (old format) or when the row is the `default` alias (real name from the description, guarded by the ` · ` separator so a blurb never leaks in), and a concrete row arriving after the alias row upgrades the entry's name and efforts. Tests pin the real 2.1.x catalog shape (blurb descriptions, alias+concrete pair, alias-only catalog, old format, malformed rejection).

- Streaming reveal no longer lags behind the turn. The character-reveal animation drained its backlog at ~0.45s of text, and every text/reasoning part of a still-streaming message animated independently, so reasoning and text were often still typing while the tool call below them had already rendered. Reveal is now sequential: only the last part of a streaming message animates, and when a successor part appears (or the message completes) the remaining backlog flushes instantly, so each phase of a turn finishes before the next begins. The active catch-up window halves to 0.22s (smoothing exists to polish chunk-to-chunk cadence, not to queue visible text behind the stream), and a single arrival larger than 400 chars reveals all but the last 400 instantly, so a buffered reasoning dump no longer types out for seconds while later parts wait below. Mounts still snap to the current text (no replay) and wholesale text replacement (edit/revert) still snaps.

- Claude transcripts now preserve text/tool interleaving. Both the parent turn (`harnesses/claude-cli/execution.ts`) and subagent child timelines (`child-timelines.ts`) accumulated ALL of a turn's text into a single text part created when the first text arrived, so text generated after tool calls was appended above the tool rows and a turn rendered as one text block followed by every tool call. Text is now segmented: each `tool-start` closes the open text segment and following text opens a new part created after the tool row, with a monotonic `partClock` (parts sort by `created_at`, and same-millisecond ties would make the order ambiguous). Consecutive text without a tool between still merges into one part as before, so text-only turns (and the single-text-part assumption behind Claude Edit/Undo history matching) are unchanged, and the streamed-text reconciliation (`text-final` suffix check) now runs per segment against that segment's own deltas.

### Removed

- Make model providers read-only: provider create, rename, and delete disappear from every layer, leaving providers as catalog entries owned by `~/.prokopai/models.json` or a registry Sync (which can still add or replace them wholesale). The REST routes `POST/PUT/DELETE /api/config/models/providers(/:id)` are gone, `createProvider`/`updateProvider`/`deleteProvider` leave `config/models.ts`, the `ModelsConfigurationPort` and its Jean2 adapter wiring, and the SDK loses the `createProvider`/`updateProvider`/`deleteProvider` client methods, their request/response types, and re-exports (model-level CRUD and default-model selection stay). The client panel drops the "Add provider" action and `ProviderEditorForm` (deleted); provider cards keep connection controls and model add/edit/delete but no provider edit/delete buttons or dialogs, and the three provider mutation hooks (`useCreateProvider`/`useUpdateProvider`/`useDeleteProvider`) are removed. Rationale: after the OpenAI/Z.AI prune the catalog is a curated set of four known providers; hand-creating providers in the UI produced unusable entries without credentials or runtime support, and the existing catalog-file/Sync path covers real additions.

- Remove the model cost tier (budget/standard/premium) from the product surface. Tier never carried behavior beyond badges and stopped matching how people actually pick models (subscription plans, not per-token price classes). It leaves every layer: the bundled models.json template drops all tier fields, the strict schema validator accepts a file with or without them (a present-but-invalid value still fails validation, so older files keep loading unchanged and new writes simply omit the field), `ModelDefinition.tier` becomes an optional legacy-parse field, model create/update stop accepting or writing it, and the SDK `ModelWithStatus`/`CreateModelRequest`/`UpdateModelRequest` drop the field. The client loses the tier badges (model picker `$`/`$$`/`$$$`, Models panel B/S/premium chips), the Tier select in the model editor form, and the local Model type declarations; storybook fixtures follow. The pinned Capek 1.1.0 contract still *requires* tier on its model shapes (Capek main already removed it), so the runtime-configuration adapter now wraps `findModel`/`getModelsConfig` with a `withContractTier` defaulting shim (`tier: 'standard'` when absent, stored value preserved when present) that dies with the next Capek pin bump; the adapter's identity test acknowledges the two wrapped accessors and the shim gets its own unit test.

- Remove the raw OpenAI API provider and the plain Z.AI provider; the model catalog keeps DeepSeek, MiniMax, Z.AI (Coding Plan), and Codex (ChatGPT subscription). OpenAI models were duplicating the Codex provider's lineup at pay-per-token prices nobody was going to pay (a ChatGPT subscription covers them), and plain Z.AI had no models in the catalog (the coding plan variant is the supported one). The provider leaves every layer: the bundled `models.json` template (9 OpenAI models), the supported-provider/env-key sets that drive model runtime status, the API-key credential registry (so the settings panel no longer offers OpenAI or Z.AI key fields), the Capek runtime `getApiKey` accessor switch and its environment accessors, and the startup provider log. Client stale fallbacks (`gpt-4o`/`openai` as pre-hydration default model/provider, the variant-update `|| 'openai'` provider fallback) become empty strings, and the credential panel drops the removed display names. Existing installs keep their `~/.prokopai/models.json`: the openai rows surface as an Unsupported provider that can be deleted in the Models UI. Follow-ups outside this repo: the upstream models registry (`capek-dev/prokop` GitHub default for Sync) still lists OpenAI, so a merge sync can re-add it until that registry is pruned, and the Capek-side provider registry still carries the OpenAI/Zhipu AI-SDK factories (dead code until the next capek cleanup).
- Remove the per-capability permission risk levels: the memory, skills, and session-search workspace capabilities are on/off and always allowed when enabled. Prokop passes risk `'none'` to the Capek executors everywhere (the capability bridge in `adapters/capek/domain-tools.ts` keeps the risk parameter as Capek's contract; its ask parameter becomes optional), and the codex/claude dynamic-tool wrappers drop their risk plumbing and per-write ask callbacks. Stored settings are coerced at the single read boundary (`normalizeCapabilityRisk` in `domains/workspaces/record.ts`, also applied before every persist in the SQLite workspace repository), so legacy stored levels stop asking without a migration and no writer can re-introduce one; the REST settings schema no longer accepts the risk fields (sent values are stripped and normalized away). The now-dead ask plumbing goes with it: `requestMemory`/`requestSessionSearch` and the shared `requestDynamicTool` disappear from both native-harness approvals classes along with the execution ask wiring, the agent-home promotion and learning enable write `'none'`, and the client capability panels lose the five-level selector (Memory and Skills are a single toggle; Session Search keeps its include-tool-results switch). Scheduling keeps its stored setting on the Capek contract but nothing in Prokop reads it.

- Remove the agent-facing scheduler tool and the Scheduling workspace capability; the scheduling UI stays (user-facing only). The Prokop composition drops capek's `schedulerDomainPlugin` (the `scheduler` domain tool no longer reaches any harness; it was prokop-only to begin with) along with the now-dead capek scheduler host chain: the `current.scheduler-host` process value plugin, `configureJean2SchedulerHost` and its `createSchedulerHostDeps` bootstrap wiring, the `adapters/capek/scheduler.ts` adapter and its test, and the `installSchedulerToolFallback` compatibility registration. The scheduler domain fallback catalog disappears with it, so the `/api/tools` catalog no longer lists `scheduler` under any source. Workspace settings lose the `scheduling` block (zod schema field, the Workspace settings dialog Scheduling section/panel/icon, and the client settings snapshot/save wiring); stored settings keep a legacy `scheduling` key harmlessly (loose schema, nothing reads it), same pattern as the workflow removal. The scheduled-job runner drops its anti-recursion `scheduler` tool filter (the tool no longer exists to recurse through). Untouched: the scheduler REST routes, the scheduling ticker, the headless job runner, and the SchedulerJobModal — humans still schedule any-harness jobs through the UI; the `WorkspaceSchedulingSettings` field stays on the capek contract as an inherited, unread optional.

- Remove the workflow capability from the product surface. The Prokop composition no longer registers the Capek workflow domain plugin (`workflowDomainPlugin` leaves the agent scope and the plugin-id pin list), the learning composition omits one fewer domain key, the workspace-settings schema drops the `workflow` block, the Workspace settings dialog loses the Workflow section/toggle/panel, and the SDK stops re-exporting the workflow types. Stored workspace settings keep their `workflow` key harmlessly (the settings schema is loose and nothing reads the value). The workflow orchestrator itself lives in `@capekai/core`; removing it there (including the `goals/evaluator.ts` import of the orchestrator session and the `workflow/` directory) is the separate Capek-side cleanup branch.

### Changed

- Tool output previews in the transcript are capped and scroll inside instead of stretching the page. A shared `.tool-output-scroll` style (`index.css`) caps shell output, written-file code blocks, and expanded diff bodies at `min(24rem, 45dvh)` with a thin themed scrollbar, so a block scrolls inside up to its cap and then chains the scroll back into the transcript (no `overscroll-behavior: contain`: it blocks chaining even on blocks shorter than the cap, which trapped the wheel and stopped the session from scrolling). Header rows (command line, file path, diff stats) sit outside the scroll area; written files and diffs apply the cap only when expanded, since the collapsed line-budgeted previews never need it. The cap applies from the `sm` breakpoint (640px) up: on phones the nested scroller intercepts touch scroll before it can chain to the transcript, so mobile viewports render output fully and uncapped.
