### Changed

- Normalize harness state on the session wire so clients stop branching on harness identity and per-harness metadata keys (S11.6). A new `domains/sessions/harness-state.ts` derives a `SessionHarnessState` from the persisted harness and its metadata — compaction (pending/uncertain/boundary message id), fork (mode with the server-owned restriction reason), goal uncertainty, the native approval tool-call prefix, and capabilities (queue removal, subagent interrupt, sidebar running propagation) — and the SQLite session repository attaches it to every session it returns, so all REST and WebSocket session payloads carry it. The SDK `Session` type gains the optional `harnessState` field (additive; the per-harness metadata keys remain unchanged for the harness runtimes themselves). The client swaps its identity checks and metadata parsing for field reads: ChatView reads compaction, fork, and native-ask state from `harnessState` (including the server-provided fork-unavailable reason), the sidebar running propagation and the permission auto-approve native guard read the derived capabilities/prefix, reducing client-side harness identity branches from 26 to 9 — the remainder are the accepted per-harness surfaces (model pickers, approval labels, creation defaults). Client fixtures now mirror the wire shape.

- Move the built-in tool set under the Prokop harness directory (S11.5b physical move). The 18 baked-in tools, their registry, and their tests relocate from `src/tools/builtin/` to `src/harnesses/prokop/tools/`, making the tool set harness-owned like the composed runtime and learning runtime. The two adapter consumers no longer import harness internals: the tools-route catalog seam (`tool-source.ts`) reads the built-ins through a new installable `BuiltinToolsPort` (`application/ports/builtin-tools.ts`, installed by the composition root; with no port installed the catalog lists domain and installed tools only), and the agent-scope resolver plugins (`builtinToolsAgentPlugins`) now take the tool set as an explicit parameter that the composition profile passes. Layer rules drop the old `tools/builtin` whitelists from the infrastructure and adapter rules, the SQLite exception narrows to the Prokop tools directory (the todo tool's standalone database), and the composition-root import and legacy-order pins gain the port install. No tool definitions, execution behavior, or catalog output change.
- Simplify the built-in tool catalog from 24 to 18 tools. `edit`, `edit-range`, and `multiedit` merge into one `edit` tool that accepts string-replacement items (`oldString`/`newString`/optional `strategy`) and line-range items (`startLine`/`endLine`/`newString`) in the same atomic `edits` array, with an optional `revision` (sha256 from read-file) that fails the whole edit when the file changed since the read; string items keep the safe ordered matching passes (exact, line-endings, trailing-whitespace, indentation) and range line numbers refer to the content as it stands after preceding edits in the same call. `todowrite` and `todoread` merge into one `todo` tool (call without `todos` to read, with the full array to replace) returning the persisted state and todo-list visualization in both modes. The `ls`, `apply-patch`, and `git-worktree` tools are removed entirely: `ls` overlaps glob and read-file, `apply-patch` had zero code consumers and was redundant with the merged edit, and the divergent git-worktree lifecycle (registered but hidden by the tool policy) gives way to the application/transport worktree surfaces. The default Full-agent preconfig drops the removed names (18 → 12 entries) and the Explore subagent drops `ls`. The Capek tool policy becomes identity now that nothing needs hiding, the client file-mutation invalidation set trims to edit/write-file/shell, and the built-in registry test pins the new 18-tool set.
- Extract the shared shell-permission classification into a neutral permissions domain (S11.5a). `domains/permissions/` now owns the one policy definition point for shell operations: the risk classifier (`analyzeRisk`, `parseCommand`, `stripRedundantCd`, `resolveCommandPath`) moves out of `tools/builtin/shell/risk.ts` with a neutral structural `ShellRiskContext` (no `@capekai/tool` dependency, so the Codex hook's fake-context cast disappears), the shared path policy helpers (`isSensitivePath`, `isWithinRoot`/`isOutsideRoot`, and the symlink-following `effectivePath`) replace the per-harness copies, and a new `classifyShellCommand` owns the native-harness Bash ask building (login-shell unwrapping, risk analysis, structured ask) that previously lived in the Codex hook policy. The Prokop shell and terminal tools, the Codex pre-tool hook, and the Claude pre-tool hook all consume the domain; the Claude tool policy no longer imports from `codex-cli` (the last cross-harness value import), and its Bash classification now runs the identical domain path the Codex hook uses. A boundary gate pins the domain to SDK contracts, node builtins, and siblings. No behavior change: the same classification runs with the same outcomes for every consumer (pinned by the Codex pre-tool-hook and Claude approval suites plus the new domain tests).
- Complete the harness isolation boundary (S11.4): the server startup root no longer imports Prokop harness internals. The composed execution-scope lifecycle (initialize/dispose) becomes an installable application port (`application/ports/execution-lifecycle.ts`); the composition root installs the Prokop implementation right after `configureJean2Bindings`, and startup consumes the port helpers (`initializeExecutionLifecycle`/`disposeExecutionLifecycle`) with the same ordering (init before serving, dispose after workers stop and before the database closes). The test-only re-export of `createJean2RuntimeComposition` from the composition root is gone — the composition test imports the harness module directly — and the layer rules drop the adapter-layer harness whitelist; a new boundary gate enforces that no server source outside `harnesses/` and `bootstrap/` imports `@/harnesses/*`. No behavior change: the same functions run in the same order, now reached through the port.
- Decouple the learning coordinator from Prokop harness internals. A new `LearningRuntimePort` (`application/ports/learning-runtime.ts`) defines the per-harness learning contract: the harness identity stamped on review-created sessions, knowledge-directory resolution, and history/review-execution assembly over caller-owned persistence handles (generic Repository and Database parameters, so no harness or infrastructure type crosses the port). `harnesses/prokop/learning/index.ts` exports `createProkopLearningRuntime` implementing the port with the existing directory resolver, history, and execution adapters, plus the composition-execute test seam; `bootstrap/learning.ts` receives the runtime as a parameter, stamps `runtime.harness` instead of the hard-coded `'prokop'`, and imports no harness module — a new boundary gate pins that. The composition root passes the Prokop runtime in. Orchestration stays in the application; a future harness supplies its own runtime the same way. No behavior change.
- Give scheduled jobs a persisted owning harness and harness-agnostic headless dispatch. `scheduled_jobs` gains a `harness` column defaulting to `prokop` (existing rows backfill through the schema migration), surfaced on the SDK `ScheduledJob` record as a product extension of the neutral Capek type and settable through the create route (`CreateScheduledJobInput.harness`, validated enum; omitted means `prokop`). Execution no longer assumes the Prokop runtime: the runner resolves session identity, preconfig, and model selection as before, then dispatches the child run through a new installable `HeadlessSessionRunPort`; `HarnessRegistration` gains an optional `headless` capability, the Prokop harness implements it by entering its composed agent scope around `executeChildSession` (with an injectable test seam), and bootstrap installs a registry dispatcher that routes by the job's harness and fails closed with a recorded job error for harnesses without headless support. Job creation rejects such harnesses up front with a 400 (`harness_unsupported`), so Codex CLI and Claude CLI stay Prokop-only until they gain headless runners. The scheduled-job execution adapter and infrastructure no longer import any `harnesses/prokop` internals; the composed-scope entry for scheduled runs moved from the adapter into the Prokop headless implementation, and the S10 execution-scope gate follows it. The Capek scheduler host trigger preserves the row's harness when forwarding to the execution port.
- Add universal server-side session-title regeneration for every harness. Codex CLI and Claude CLI sessions no longer report title generation as unsupported: their harness registrations supply the new application title use case (`createSessionTitleRegeneration` behind a `TitleGenerationPort`), which mirrors the Capek semantics exactly: without force it only regenerates default titles that were never renamed manually, it reads the newest transcript page, persists the new title, broadcasts `session.renamed` to the session audience, and reports `title_generation_error` to the requesting origin when generation returns nothing or throws. Chat sends and edits on external-harness sessions fire this regeneration automatically once the awaited turn settles; Prokop sessions keep Capek's own auto-title timing after the user message. The Prokop harness implementation is unchanged, and the planned per-harness title-model picker lands behind the same port.
